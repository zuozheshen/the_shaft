# the-shaft-issue-runner

项目工作模板。入口：`Run issue #<number>`。AGENTS.md 将该请求路由到本文件。
人工启动 Agent；不需要长 Prompt，不安装额外插件，不运行后台调度。

## 读取与续接

1. 读取 AGENTS.md、PROJECT_STATE.md，检查包含 project.godot 的根目录。
2. 通过 `git remote -v` 确定仓库，读取当前 Issue 正文及全部评论。优先使用已连接 GitHub 工具；否则使用已授权且已安装的 CLI。连接不可用时报告缺失信息，不猜测 Issue，不请求 Token。
3. 检查 `git status --short`、HEAD、当前分支、worktree、diff 和必要历史。不要把未 fetch 的 remote-tracking ref 声称为远端最新状态。
4. 找出冻结规格、当前阶段、计划版本、风险、有效审批及后续修订。以最新有效修订续接；普通评论中的引用或示例不构成审批。
5. 读取相关脚本、场景、资源与测试。核对 Issue 和实际结构；有冲突时明确列出，不猜测设计意图，不自行扩大范围。

PROJECT_STATE 缺失时说明事实来源缺口；只有 Issue 已授权创建时才补建。不得为了启动任意任务自动添加另一份项目状态。

## 阶段与门

| 条件 | 下一步 |
| --- | --- |
| 需求未冻结 | DESIGN：只读分析，待人决定 |
| 冻结 GREEN | 输出具体 PLAN 后可 BUILD |
| AMBER 无对应批准 | 回写 PLAN，停止等待审批 |
| AMBER 已批准且范围/基线相符 | 直接续接 BUILD，不重复申请同一批准 |
| RED | 停在明确的逐步授权门，不自主执行 |
| 规格/基线有实质冲突或超出批准范围 | 报告变化，重新过门 |

按影响而非后缀分级。场景关系、公共 API、Input/Camera/Interaction 接线、多运行时对象关系至少 AMBER。
不得把重复的 `Run issue` 当成 AMBER 批准，也不得自行下调已冻结等级。
审批需指向计划版本和范围；用户或负责审查的 ChatGPT 可以批准，评论中的附加约束也是计划的一部分。

## PLAN 模板

- Issue / 计划版本 / 阶段 / 风险及理由。
- 目标、范围、非目标、验收标准。
- 实际基线：repo、HEAD、branch、工作区、入口、相关 Manager/数据源/测试。
- 实现步骤及每个预计文件/场景的原因；不只是重排 Issue。
- 隔离方案、base commit、依赖的尚未进入 main 的历史。
- 统一测试、结构正反例、失败诊断、Godot 人工操作。
- 与仓库冲突、未知项、待批准内容；区分“预期”与“已验证”。

## 隔离 BUILD

1. 开始前重新核对审批、HEAD、工作区及目标分支是否已存在。续接已有同 Issue worktree 时先验证归属，不重复创建。
2. 默认新分支 `dev/<number>-<short-name>`。优先使用仓库外获准目录中的 worktree，从已核实基线创建；Issue 的具体隔离要求优先。
3. 先确认目标路径在原仓库外，且不会覆盖已有目录/分支。不得在仓库内部创建第二个项目。工具权限失败走正常权限审批；无法安全创建时停止报告。
4. 保留用户改动，不自动 stash/reset，不切换无关功能 checkout 开发。记录 base 和合并顺序依赖；不为“从 main 开始”退回旧架构，也不擅自 rebase。
5. 一次只改一个 Issue；沿用正式数据和现有 Manager。范围外故障记录到当前 Issue，不顺手修业务。
6. 在 worktree 根执行 `powershell.exe -NoProfile -File .\tests\run_all_tests.ps1`，也支持 pwsh。按 tests/README.md 处理 Godot 路径与失败。
7. 测试失败先运行最小复现；同一根因最多自动重试 2 次，第 3 次立即停止并写回诊断。单阶段失败不得循环重跑全量入口，重复权限请求、重复命令或阶段重入同样触发停止。
8. 自动进入 REVIEW：检查相对 base 的 diff，确认测试是否对应最终内容。修改后仅重跑受影响且必要的检查。
9. 确有需要时创建本地 commit：先 `git diff --check` 和审查文件，显式逐文件暂存，再检查 staged diff，提交信息关联 Issue。失败或工作未完成不得写成已完成。
10. 不自主 push、merge、force-push、删除远端分支、改共享历史或权限。不得通过 GitHub 写文件工具间接替代 push/commit 绕过限制。

## REVIEW 与 GitHub 交接

BUILD 后把下列信息写回当前 Issue，供 ChatGPT/用户直接读取：

- 阶段、Issue、计划/审批评论链接及有效修订。
- 实际修改文件、实现摘要、为何需要这些改动。
- 每项检查命令、引擎版本、exit code、通过/失败/未执行、日志中的可复核摘要。
- Scene Contract 检查和损坏结构反向测试；统一入口结果。
- 已知限制、范围外故障、计划偏差及原因。
- Godot 人工体验点、用户验收是否执行；不要用自动通过代替体验验收。
- base branch/hash、当前 branch、本地 commit、是否 push、实际 PR 链接（如有）。
- 若 base 未入 main，写明整合前置依赖；不称为可独立合入旧 main。
- 待用户决定事项及当前停止点。

写回前读取评论以去重；更新自己的对应交接评论或追加明确的新阶段区块，不覆盖原规格或人工内容。
正文使用结构化工具参数；CLI 使用 body-file，保留真实换行。不要把凭据或完整敏感日志写入 GitHub。
如果只有本地 commit，写明“本地、未 push”，不伪造远端 commit/PR 链接；通过 Issue 记录文件差异与结果，完整远端代码审查等待用户授权 push。
回写失败时在当前任务中明确“未同步”及可重试原因，保留证据；恢复后先查询是否实际写入，避免重复。
任务中已给出的有效授权可继续使用；不因技能中的一般默认限制反复请求批准。
该工程交接不授权飞书同步；开发日志按独立工作流处理。

## 维护演练清单

每次评审流程变更时，按下表记录“实际执行”或“规则推演”，不能混淆。
动态演练结果写入 Issue，模板不保存正在进行的任务状态。

| 场景 | 预期 |
| --- | --- |
| 冻结维护任务 / GREEN | PLAN → 隔离 BUILD → TEST → REVIEW → 范围内本地 commit |
| AMBER、没有计划批准 | 输出可审阅 PLAN，文件与分支保持原样 |
| AMBER、有对应版本批准 | 按批准约束续接，不重新要求整份 PLAN |
| RED 要求重写历史 | 无逐步授权时不执行 |
| 脏工作区或目标路径已存在且归属不明 | 不覆盖、不 stash/reset，报告隔离问题 |
| Issue 与真实入口冲突 | 报告冲突，不新建旧入口或第二 Manager |
| 测试 ERROR / 超时 / 缺引擎 | 非零退出，不写“通过” |
| 同一失败第 3 次出现或测试循环重入 | 触发 Circuit Breaker，停止变体尝试并回写诊断 |
| GitHub 请求超时 | 查询是否写入，再决定重试，不写“已同步” |
| 本地 commit 完成 | 回写 hash 和未 push 状态，停在 push / merge 前 |

这是可审阅的 Agent 协议，不是 OS 权限拦截器；v1 不宣称阻止所有越权行为或提供无人值守安全保证。
